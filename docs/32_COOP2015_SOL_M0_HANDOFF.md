## 1. Срочные подтвержденные находки под текущие блокеры Sol Max

### Блокер 1: Загадка «снаряда 0x160» и краш в Actor Remove
- **Наблюдение Sol Max в 2022:**
  Объект базовой фабрики снарядов имеет размер `0x160`. Вызов `Actor Remove` пишет во флаги актора по оффсету `+0x16c`, что вызывает порчу памяти (out-of-bounds write).
- **Подтверждение из исходников 2015:**
  - **Файл:** `src_orig\game\projectile.h`, строка 130:
    ```cpp
    BEGIN_EXTENDED_KEX_CLASS(kexFireballFactory, kexGameObject); // НАПРЯМУЮ ОТ GAMEOBJECT!
    ```
  - В отличие от `kexFireballSpawner` (который наследует `kexActor`), класс `kexFireballFactory` — это **базовый `kexGameObject`**!
  - `kexGameObject` **НЕ ИМЕЕТ** полей актора (`radius`, `height`, `bounds`, `flags` на `+0x16c`).
  - Метод `kexActor::Remove` выполняет `flags &= ~(AF_SOLID|...);` на смещении `+0x16c`.
- **Инженерное решение для Sol Max:**
  Объекты размером `0x160` — это `kexGameObject`, а не `kexActor`. Для них категорически запрещено вызывать `Actor::Remove` (RVA `0x1a02b0`). Они удаляются исключительно установкой флага `bStale` (в 2022 это флаги `0x2004` в базовом заголовке), после чего штатный sweep возвращает их в пул.

### Блокер 2: Удержание ссылки `sourceOwner + 0x148` на узле врага (`refs = 1`)
- **Наблюдение Sol Max в C08/C10:**
  После попадания P2 по врагу и вызова `SetTarget(enemy, nullptr)` узел P2 успешно освобождается (`refs = 0`). Однако узел врага остается с `refs = 1` из-за того, что объект удара/снаряда удерживает ребро `sourceOwner + 0x148 → enemy.node`.
- **Архитектурный факт из KEX-движка:**
  В KEX-движке любой источник урона, снаряд или динамический свет связывается с владельцем и целью:
  - В 2015 было одно поле `target` в `kexGameObject`:
    - При выстреле снаряда: `proj->SetTarget(shooter)` (снаряд держит стрелка, чтобы не сталкиваться с ним).
    - При ударе снаряда об актора: `contactActor->InflictDamage(this, damage)` передает снаряд как инстигатор. Враг устанавливает `ai->SetTarget(instigator->Target())`.
  - В 2022 Nightdive добавили второе явное поле: `sourceOwner` на смещении `+0x148` наряду с `target` на `+0x28`.
- **Инженерное решение для Sol Max:**
  1. В C08 подтверждена сигнатура сеттера `SetSourceOwner` (RVA `0x1a17c0`):
     `Win64 RCX = actor, RDX = null` очищает `[actor + 0x148]` и выполняет штатный атомарный `lock xadd dword ptr [oldNode + 0x40], -1`.
  2. Чтобы узел врага гарантированно получил `refs = 0` после боя, **все порожденные снаряды и акторы эффекта удара** обязаны вызвать `SetSourceOwner(nullptr)` (RVA `0x1a17c0`) до вызова своего `Remove`.

### Блокер 3: Предотвращение dangling pointer при смерти цели на лету
- **Проблема в 2022:**
  Если враг уничтожен или удален из мира, пока к нему летит снаряд (или снаряд находится в фазе детонации), ссылка на врага остается висеть.
- **Подтверждение из исходников 2015 (`projectile.cpp:111, 209`):**
  Движок Kaiser'а решает это превентивным сбросом в каждом тике мышления снаряда:
  ```cpp
  if(homingActor->Removing() || homingActor->Health() <= 0)
  {
      SetHomingTarget(NULL); // АВТОМАТИЧЕСКИЙ СБРОС И ДЕКРЕМЕНТ REFCOUNT
  }
  ```
- **Инженерное решение для Sol Max:**
  При уничтожении любого актора (в точке `OnDeath` или перед вызовом `Remove`), если в мире есть активные снаряды, нацеленные на него, необходимо сбросить их целеуказатель в `nullptr`.

### Блокер 4: Двухпроходный Teardown уровня и выхода игрока
- **Подтверждение из исходников 2015 (`game.cpp:1229–1243`, `kexGameLocal::RemoveAllGameObjects`):**
  В оригинальном движке удаление объектов никогда не выполняется в один проход, так как циклические ссылки взаимно блокируют очистку (`bStale && RefCount() <= 0`).
  Kaiser использует двухпроходный алгоритм:
  ```cpp
  // ПРОХОД 1: Де-референс ВСЕХ целей
  for(go = gameObjects.Next(); go != NULL; go = go->Link().Next())
  {
      go->SetTarget(NULL);
  }
  // ПРОХОД 2: Фактическое удаление (когда RefCount гарантированно равен 0)
  for(go = gameObjects.Next(); go != NULL; go = next)
  {
      next = go->Link().Next();
      RemoveGameObject(go);
  }
  ```
- **Инженерное решение для Sol Max:**
  При очистке тестовой арены (перед сменой карты или при выходе P2) запускать Проход 1:
  - Для всех тестовых акторов вызывать `SetTarget(actor, nullptr)` (RVA `0x1d35d0`) и `SetSourceOwner(actor, nullptr)` (RVA `0x1a17c0`).
  - После этого запускать Проход 2 (`Remove`), и все узлы мгновенно уйдут в `refs = 0` без зависания в памяти.

### Блокер 5: Риск синглтона при смерти P2 (Dead PlayerUpdate vcalls)
- **Опасение Sol Max (из DOC-27):**
  «Dead secondary PlayerUpdate после 60 updates вызывает глобальные GameInstance vcalls. Длительную смерть P2 нельзя проверять текущим контроллером без предотвращения этой singleton-ветки».
- **Как это решено в проверенном коде 2015 года:**
  1. В синглплеере смерть игрока действительно запускает глобальный рестарт уровня через таймер `restartDelayTicks`.
  2. В кооперативе **мгновенный респавн и синглплеерная смерть отключены полностью**:
     - При получении смертельного урона выставляется флаг `PF_DEAD`.
     - Функция контроллера мертвого игрока переключается на `DeadMove(cmd)` (`player.cpp:619`), которая просто гасит скорость и опускает высоту глаз `viewZ`. Никаких глобальных перезапусков `GameInstance` не вызывается.
     - Локальный игрок переходит в режим **наблюдателя (Spectator)**: камера 90 тиков смотрит на свой труп, затем привязывается к живому тиммейту (`UpdateSpectator`, `playLoop.cpp:787`).
     - Если погибает **вся команда целиком** (все игроки имеют `PF_DEAD` в течение 60 тиков, `UpdateCoopDeaths`, `playLoop.cpp:767`), хост выполняет безопасный `RestartLevel()`, восстанавливая стартовый снимок `RestoreCoopPlayers()`.
     - Если хотя бы один игрок дошел до выхода, мертвый игрок восстанавливается до `maxHealth` в момент смены карты (`playLoop.cpp:275`).
- **Инженерное решение для Sol Max:**
  В контроллере P2 для M0 не нужно вызывать синглплеерную логику перезапуска после смерти. Достаточно переводить P2 в состояние `PF_DEAD` с вызовом пассивного `DeadMove`, полностью блокируя синглтон-вызовы перезапуска карты до тех пор, пока жив P1.

## 2. Краткий чеклист для Sol Max перед тестом C14

1. [ ] **Фабрики 0x160:** Убедиться, что скрипты Frida не передают указатели базовых фабрик `kexGameObject` в функцию `Actor::Remove` (RVA `0x1a02b0`).
2. [ ] **Сброс `sourceOwner`:** В сценарии попадания снарядом перед завершением теста вызвать нативный `SetSourceOwner(impactActor, nullptr)` на RVA `0x1a17c0`.
3. [ ] **Сброс `target`:** Вызвать `SetTarget(enemyActor, nullptr)` на RVA `0x1d35d0`.
4. [ ] **Проверка `node->refcount`:** Наблюдать падение refcount обоих узлов (P2 и enemy) до 0 и их успешный уход в deferred pool sweep.
5. [ ] **Смерть без краша:** В тесте смерти P2 подавлять синглтон-ветку перезапуска уровня, оставляя P2 в пассивном `DeadMove` (проверено 2015 годом — это штатный кооперативный режим).
