# PowerSlave Exhumed Together — Проверка совместимости Native KEX 2022 и ENet-прототипа (Compatibility Check)

**Документ:** `docs/35_NATIVE_ENET_COMPATIBILITY_CHECK.md`  
**Дата аудита:** 01 ноября 2026 г.  
**Контекст этапа:** Завершение Milestone M0 исследователем Sol Max и подготовка к разработке первого нативного сетевого прототипа P1 + P2 (Milestone M1).  
**Область аудита:** Независимое сопоставление замороженного сетевого интерфейса ENet (`tools/enet-prototype`, [DOC-29](29_ENET_FINAL_ACCEPTANCE.md), [WIRE_PROTOCOL.md](../tools/enet-prototype/docs/WIRE_PROTOCOL.md)) с подтверждёнными нативными контрактами движка KEX 2022 (`anubis_Shipping_Steam_x64.exe`, SHA-256 `b8f131037187ca8d0a282527fb6f55a2012241d5b9dac8bf2038baf35b71a76d`, Evidence C01–C19, статические dossiers Ghidra 12.2, ресурсы `PowerslaveEX.kpf`).  
**Статусы верификации:**
- `CONFIRMED` — доказанное фактическое несоответствие между нативным кодом и сетевым прототипом.
- `POTENTIAL` — потенциальный интеграционный риск или архитектурное ограничение, требующее решения при реализации адаптера.
- `UNKNOWN` — параметр или поведение, не установленные окончательно в нативном бинарнике.
- `BLOCKED_BY_M0` — зависимость, заблокированная незавершёнными или не принятыми нативными экспериментами M0 (включая C20).

## 2. Анализ состояния игрока (Player State)

### 2.1 Несоответствие нумерации и типов оружия (INC-01)

* **Нативное доказательство и источник:**  
  В дистрибутивном пакете `PowerslaveEX.kpf` (Evidence `E010_KPF_SELECTED_TEXT.json`) конфигурационный файл `defs/weaponInfo.txt` содержит ровно 8 определений оружия:
  1. `Wep_Machete` (`persistant 1`, `maxAmmo 0`) $\to$ Слот 0.
  2. `Wep_Pistol` (`maxAmmo 60`) $\to$ Слот 1.
  3. `Wep_M60` (`maxAmmo 38`) $\to$ Слот 2.
  4. `Wep_Bombs` (`maxAmmo 15`) $\to$ Слот 3 (гранаты).
  5. `Wep_FlameThrower` (`maxAmmo 65`) $\to$ Слот 4 (огнемёт).
  6. `Wep_CobraStaff` (`maxAmmo 16`) $\to$ Слот 5.
  7. `Wep_RingOfRa` (`maxAmmo 250`) $\to$ Слот 6.
  8. `Wep_Manacle` (`maxAmmo 6`) $\to$ Слот 7 (браслеты Килмаат).  
  
  В `defs/actors/items.txt` свойства `weaponSlotToGive` для предметов строго подтверждают эту привязку:
  - `Item_Weapon_Pistol` $\to$ `weaponSlotToGive 1`
  - `Item_Weapon_M60` $\to$ `weaponSlotToGive 2`
  - `Item_Weapon_Bomb` $\to$ `weaponSlotToGive 3`
  - `Item_Weapon_FlameThrower` $\to$ `weaponSlotToGive 4`
  - `Item_Weapon_CStaff` $\to$ `weaponSlotToGive 5`
  - `Item_Weapon_Ring` $\to$ `weaponSlotToGive 6`
  - `Item_Weapon_Manacle` $\to$ `weaponSlotToGive 7`  
  
  В нативном эксперименте C19 вызов `giveWeapon(p2, 1, 0)` (`0x1401e06d0`) выдал именно пистолет, а в C16 кобра выдавалась в слот 5.

* **Соответствующий сетевой интерфейс:**  
  Файл `tools/enet-prototype/include/net_protocol.h` (строки 96–105):
  ```cpp
  enum WeaponType : uint8_t {
      WEAPON_MACHETE = 0,
      WEAPON_PISTOL = 1,
      WEAPON_M60 = 2,
      WEAPON_FLAMETHROWER = 3,  // <-- ОШИБКА: в KEX это Bombs (3)
      WEAPON_GRENADES = 4,      // <-- ОШИБКА: в KEX это Flamethrower (4)
      WEAPON_COBRA = 5,
      WEAPON_RING = 6,
      WEAPON_COUNT = 7          // <-- ОШИБКА: отсутствует Manacle (7)
  };
  ```
  В `WIRE_PROTOCOL.md` (§4.2, сообщение `MSG_INPUT_COMMAND`): поле `selectedWeapon` документировано как `Requested weapon index 0..6`.

* **Реальная причина конфликта:**  
  Прототип ENet создавался на основе ранних эскизов без сверки с реальными текстовыми дефами KPF 2022 года. В результате:
  1. Слоты 3 и 4 взаимно инвертированы (выбор гранат в сети приведёт к переключению на огнемёт в движке и наоборот).
  2. Восьмое оружие кампании (`Wep_Manacle`, слот 7) полностью отсутствует в перечислении, из-за чего выбор Браслетов клиентом будет отклонён валидатором диапазона `0..6`.

* **Критичность:** **HIGH**. Приводит к рассинхронизации выбора оружия и невозможности использования финального оружия кампании.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Поле `selectedWeapon` в `MsgInputCommand` передаётся как `uint8_t`, а маска `weaponMask` в `PlayerStateSnapshot` — как `uint32_t`. Байтовый размер структуры на проводе не изменится. Требуется исправить значения в `enum WeaponType` и увеличить константу `WEAPON_COUNT = 8`.

* **Необходимость согласования с Sol:** **Да.** Адаптер Sol Max должен использовать единый с сетью маппинг слотов.

### 2.2 Базовые значения здоровья и патронов (INC-02)

* **Нативное доказательство и источник:**  
  В `PowerslaveEX.kpf` файл `defs/actors/misc.txt` определяет базового персонажа:
  ```
  Actor Obj_Player {
      classname "kexSlavePuppet"
      health 200
      ...
  }
  ```
  В `defs/weaponInfo.txt`: у пистолета `maxAmmo 60`.  
  В нативном дизассемблере функция `Player.GetHealth` (`0x1401dfa20`) читает 16-битное беззнаковое слово по смещению `actor + 0x17a`. Если актор отсутствует, функция проверяет сложность через `GameInstance + 0x158`: при сложности 1 возвращает 100 (`0x64`), в остальных случаях — 200 (`0xc8`).  
  В эксперименте C19 (Karnak Sanctuary) при спавне и после респавна по клавише 'E' Pupppet получил:
  - `health = 200`
  - `pistol counter = 60`  
  *(Примечание: значение 200 HP подтверждено для исследованного профиля и карты, но не объявляется универсальным для всех сложностей и уровней без дополнительных проверок).*

* **Соответствующий сетевой интерфейс:**  
  Файл `tools/enet-prototype/include/net_protocol.h` (строки 108–109):
  ```cpp
  constexpr uint16_t DEFAULT_PISTOL_AMMO = 50;
  constexpr int32_t DEFAULT_HEALTH = 100;
  ```
  В `WIRE_PROTOCOL.md` (§4.2, §4.3): документация указывает `health (int32_t, 0..100)` и сброс патронов на 50 (`defaultAmmo = 50`). В `PlayerParticipant::resetToStarterLoadout` жёстко выставляются `health = 100` и `ammo = 50`. Структура `MsgRespawnConfirm` передаёт `defaultAmmo` (50), но вообще не содержит поля для стартового здоровья.

* **Реальная причина конфликта:**  
  Использование дефолтных констант классических шутеров (100 HP, 50 патронов) вместо значений KEX 2022.

* **Критичность:** **MEDIUM**. При респавне через сетевой прототип удалённый клиент визуально получит 100 HP и 50 патронов, тогда как нативный движок хоста установит 200 HP и 60 патронов.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Поле `health` сериализуется как знаковый 32-битный `int32_t` (`ByteWriter::writeInt32`), а патроны — как `uint16_t`. Сериализатор не содержит проверок на диапазон `0..100` (это ограничение было только в комментариях документации). Значения `DEFAULT_HEALTH = 200` и `DEFAULT_PISTOL_AMMO = 60` могут быть обновлены в заголовке без ломки wire protocol.

* **Необходимость согласования с Sol:** **Да.** Согласовать стартовые константы для адаптера M1.

### 2.3 Единицы измерения углов обзора (INC-03)

* **Нативное доказательство и источник:**  
  Движок KEX 2022 производит расчёт углов ориентации акторов (`yaw`, `pitch`) строго в **радианах** в диапазоне $[-\pi, +\pi]$ (от $-3{,}14159$ до $+3{,}14159$).  
  - В C19 зафиксировано: стартовая ориентация спавна `yaw = -3.137605` (что соответствует развороту на юг $\approx -\pi$).
  - В C16 зафиксировано: выстрел в стену под углом `yaw ≈ π/2`.

* **Соответствующий сетевой интерфейс:**  
  В `WIRE_PROTOCOL.md` (§4.2, `MSG_INPUT_COMMAND`):
  - `pitch (float)`: *Vertical view angle degrees*.
  - `yaw (float)`: *Horizontal view angle degrees*.  
  В `tools/enet-prototype/src/client_interpolator.cpp` (строки 7–11):
  ```cpp
  static float angleLerp(float a, float b, float alpha) {
      float diff = std::fmod(b - a + 180.0f, 360.0f);
      if (diff < 0.0f) diff += 360.0f;
      diff -= 180.0f;
      return a + diff * std::clamp(alpha, 0.0f, 1.0f);
  }
  ```

* **Реальная причина конфликта:**  
  Интерполятор клиента рассчитывает на градусную меру ($360^\circ$). Если движок передаст угол в радианах (например, $\pi \approx 3{,}14$), алгоритм `angleLerp` сочтёт этот поворот равным $3{,}14^\circ$. Клиентские марионетки будут визуально «заморожены» или будут вращаться с колоссальными геометрическими искажениями.

* **Критичность:** **HIGH**. Дезориентация и полная поломка рендеринга направления взгляда удалённых игроков.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** На проводе передаются сырые `float`. Исправление требует лишь явного соглашения: либо Sol Max Adapter переводит радианы в градусы перед отправкой (`deg = rad * 180.0f / M_PI`) и обратно при приёме ввода, либо `angleLerp` в интерполяторе переводится на модульную арифметику $2\pi$. Рекомендуется выполнять нормализацию в градусах на уровне адаптера, сохраняя контракт `WIRE_PROTOCOL.md`.

* **Необходимость согласования с Sol:** **Да.** Зафиксировать единицы измерения в интерфейсе `IEngineReplicationAdapter`.

### 2.4 Смещение камеры по высоте ViewZ (INC-04)

* **Нативное доказательство и источник:**  
  В экспериментах C17 и C19 проверены смещения камеры в объекте `Player`:
  - `Player + 0x130 = 104.0f`
  - `Player + 0x13c = 104.0f`
  - `Player + 0x134 = 0.0f`, `Player + 0x148 = 0.0f`  
  В KEX координата $Z$ марионетки указывает на основание (ноги) персонажа (в C19: `spawnZ = 1152`), а виртуальная камера располагается на высоте $Z + 104 = 1256$.

* **Соответствующий сетевой интерфейс:**  
  `PlayerStateSnapshot` передаёт кортеж `posX, posY, posZ`.

* **Реальная причина конфликта:**  
  Отсутствие спецификации точки привязки $Z$. Если клиент установит камеру от первого лица ровно в `posZ`, точка обзора окажется на уровне пола.

* **Критичность:** **LOW**. Не ломает сетевой протокол, является внутренним правилом клиентского адаптера рендеринга.

* **Возможность исправления без изменения Wire Protocol:** **ДА.**

* **Необходимость согласования с Sol:** Нет.

### 2.5 Отсутствие передачи максимального здоровья (INC-05)

* **Нативное доказательство и источник:**  
  В оригинальной кампании сбор анкхов (`Item_Health_Ankah1..5`, RVA `0x1401e0910`) перманентно увеличивает базовый контейнер максимального здоровья игрока вплоть до 2000 HP (`docs/18_PICKUPS_AND_INVENTORY.md`). Полные сферы здоровья восстанавливают здоровье до актуального `maxHealth`.

* **Соответствующий сетевой интерфейс:**  
  В `net_protocol.h` (`PlayerStateSnapshot`) и `replication_protocol.h` (`EntitySnapshot`) передаётся текущее `health` (`int32_t`), но отсутствует поле `maxHealth`. Поле `maxHealth` объявлено только в C++ структуре `ActorStateInfo` (`engine_adapter.h`), но не попадает на провод.

* **Реальная причина конфликта:**  
  В прототипе предполагалось статическое максимальное здоровье (100 HP).

* **Критичность:** **MEDIUM**. Без знания `maxHealth` удалённый клиент не может корректно отрисовать шкалу здоровья (HUD health bar percentage) для союзников.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** В структуре `EntitySnapshot` (55 байт) имеется 4-байтное поле `meta` (`uint32_t`). Для сущностей типа `PLAYER` поле `meta` может транслировать актуальный `maxHealth`, не нарушая замороженный размер кадра.

* **Необходимость согласования с Sol:** **Да.**

### 2.6 Избыточное поле брони (INC-06)

* **Нативное доказательство и источник:**  
  Анализ исходных скриптов и определений актеров KEX 2022 (`defs/actors/items.txt`) показывает полное отсутствие сущностей брони (Armor). Защита игрока регулируется только текущим HP и временным Power-Up артефактом.

* **Соответствующий сетевой интерфейс:**  
  `PlayerStateSnapshot::armor` (`int32_t`, 4 байта).

* **Критичность:** **LOW**. Поле не вызывает ошибок, но расходует 4 байта в каждом снапшоте игрока.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Поле остаётся на проводе равным 0 либо может быть переиспользовано под таймер `Weapon Boost` (`Player + 0xa0`).

* **Необходимость согласования с Sol:** Нет.

## 3. Анализ поколений игроков и марионеток (Player/Puppet Generations)

### 3.1 Сосуществование старого Puppet и нового поколения (INC-07)

* **Нативное доказательство и источник:**  
  В C19 доказан ключевой нативный сценарий жизненного цикла:
  1. Марионетка P2 первого поколения (`node 0x13374780`) погибла от атаки противника (`health 8 -> -12`, флаг `PF_DEAD` `0x200`).
  2. Нативный `Remove` пометил старую марионетку, но её узел остался в памяти с `refcount = 2`, так как активный снаряд кобры (`0x133e1a20`) удерживал ссылку через `SourceOwner + 0x148`.
  3. По нажатию клавиши 'E' нативный `Reset` отвязал старый узел от контекста игрока, и через `kexPuppet::Spawn` была создана **новая марионетка поколения 2** (`node 0x133749c0`) на **том же самом объекте `Player`** (`0x2ba9920`).
  4. Обе марионетки одновременно присутствовали в памяти: старая удерживалась снарядом до момента его естественной выгрузки, а новая перемещалась и принимала пользовательский ввод.

* **Соответствующий сетевой интерфейс:**  
  В `WorldReplicationHost` и `WorldReplicationClient` хранилище сущностей организовано как:
  ```cpp
  std::unordered_map<uint32_t, std::shared_ptr<NetworkEntity>> m_replicatedEntities;
  ```
  Ключом является исключительно 32-битный `entityId`.  
  В методе `WorldReplicationClient::onMsgEntitySpawn` (строки 824–840):
  ```cpp
  if (spawn.entityGeneration > it->second->generation) {
      // При получении нового поколения с тем же entityId
      if (m_visualObserver) {
          m_visualObserver->onEntityVisualDespawn(spawn.entityId, it->second->generation, DespawnReason::REPLACED);
      }
      m_interpolator.onEntityDespawned(spawn.entityId);
      m_replicatedEntities.erase(it); // <-- Старый Puppet немедленно удаляется
  }
  ```
  Кроме того, в `WorldReplicationHost::allocateEntityId` тип `EntityType::PLAYER` не обрабатывается и возвращает 0; игроки принудительно привязаны к статическим слотам `1001 + slotId`.

* **Реальная причина конфликта:**  
  Прототип рассматривает игрока как единую монолитную сущность с постоянным `entityId`. Нативный же KEX разделяет долгоживущий логический контекст (`kexPlayer`, живёт всю карту) и короткоживущие физические тела (`kexSlavePuppet`, создаются заново при каждом респавне).

* **Анализ защиты от устаревших пакетов (Stale Packet Immunity):**
  - **CONFIRMED PASS.** Механизмы фильтрации протокола ENet полностью предотвращают повреждение нового поколения:
    1. `MsgInputCommand` отбрасывается, если `connectionGeneration` устарел.
    2. `MsgWorldEventConfirm` (урон) требует совпадения `targetGeneration == entity->generation`. Урон старому поколению N отбрасывается клиентом и не повреждает поколение N+1.
    3. `MsgRespawnRequest` проверяет монотонный `deathSequence == slot.deathCounter`.
    4. `MsgWorldSnapshot` игнорирует сущности с несовпадающим поколением.

* **Критичность:** **MEDIUM**. Если старый Puppet не требует отдельного визуального отображения на клиентах в виде трупа, конфликт нивелируется host-authoritative моделью (хост хранит pending-узел локально до естественного уничтожения). Если же требуется реплицировать тело старого игрока, оно не может делить один `entityId` с новым игроком.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Сообщение `MsgRespawnConfirm` уже содержит отдельное поле `newEntityId` (`uint32_t`). Адаптер Sol Max может генерировать уникальный `entityId` для каждого нового воплощения Puppet, сохраняя `slotId` для связи с игроком.

* **Необходимость согласования с Sol:** **Да.**

## 4. Потоки и игровой тик (Threading & Game Tick)

### 4.1 Небезопасность вызовов KEX из рабочего потока ENet (INC-09)

* **Нативное доказательство и источник:**  
  Все нативные эксперименты (C01, C05, C08, C13, C16, C17, C19, C20) подтверждают:
  - Игровой цикл KEX 2022 выполняется строго в рамках единого потока симуляции (`simulation_tid`, например TID 30556 в C19, TID 22172 в C17).
  - Входные точки тика: `GameInstance::StateTick` (`0x1401b6ec0`), `Player::Update` (`0x1401dfe30`), `Puppet::Tick` (`0x1401db8a0`).
  - Внутренние структуры KEX (таблица отложенного удаления актеров `DAT_140af3380`, пулы классов `kexNodePool`, списки секторов, структуры оружия и игроков) **не защищены мьютексами или спинлоками**.
  - Любой вызов нативных функций (`Spawn`, `Reset`, `Remove`, `Damage`, `GiveWeapon`) из сетевого потока вызовет немедленный фатальный сбой памяти (Data Race / Access Violation).

* **Соответствующий сетевой интерфейс:**  
  В текущем автономном прототипе `ENetHostServer::poll()` выполняет опрос сокетов (`enet_host_service`) и шаг симуляции (`m_sim.tick()`) последовательно в одном потоке. В интерфейсе `IEngineReplicationAdapter` методы изменения состояний (`notifyDamage`, `notifyPickupCollected`, `registerActor`) захватывают внутренний мьютекс `m_hostMutex` и немедленно вызывают `m_server.broadcastPacket` $\to$ `enet_peer_send`.  
  Однако ENet API (`enet_peer_send`, `enet_host_service`, `enet_host_flush`) **также не является потокобезопасным**. Вызов методов адаптера из потока симуляции KEX при параллельно работающем потоке ENet приведёт к порче структур ENet.

* **Реальная причина конфликта:**  
  В автономном прототипе сетевой поллинг и симуляция были объединены. При интеграции с реальным движком KEX эти два контура обязаны быть физически изолированы в разных системных потоках.

* **Критичность:** **CRITICAL**. Без двухсторонней изоляции очередей стабильная работа игры невозможна.

* **Минимальный контракт очередей обмена:**

```
+-------------------------------------------------------------------------+
|                        KEX SIMULATION THREAD                            |
|  - GameInstance::StateTick (0x1401b6ec0)                                |
|  - Native Actors / Physics / Collisions / Damage                        |
+-------------------------------------------------------------------------+
            |                                           ^
            | (Pushes State Events)                     | (Drains Inbound Cmds)
            v                                           |
+-----------------------+                   +-----------------------+
|  OUTBOUND EVENT QUEUE |                   |  INBOUND COMMAND QUEUE|
|  - Lock-Free / Mutex  |                   |  - Thread-Safe MPSC   |
|  - Dynamic Batches    |                   |  - Max 128 pkts/slot  |
|  - Zero ENet Calls    |                   |  - Validated Payloads |
+-----------------------+                   +-----------------------+
            |                                           ^
            | (Drains & Sends via ENet)                 | (Pushes Client Pkts)
            v                                           |
+-------------------------------------------------------------------------+
|                          ENET WORKER THREAD                             |
|  - enet_host_service() polling loop                                     |
|  - 1200B Dynamic Batching & Frame Reassembly                            |
|  - Zero Native KEX Calls                                                |
+-------------------------------------------------------------------------+
```

1. **Inbound Queue Contract (Сетевой поток $\to$ Поток симуляции KEX):**
   - Сетевой рабочий поток принимает пакеты через `enet_host_service`, выполняет парсинг заголовка `MsgHeader`, валидацию диапазона полей и проверку эпохи `mapEpoch`.
   - Валидные структуры команд (`MsgInputCommand`, `MsgRespawnRequest`, `MsgInteractionRequest`, события подключения/отключения) помещаются в потокобезопасную очередь входящих команд (`InboundQueue`).
   - Поток симуляции KEX в начале каждого кадра `StateTick` забирает накопленные команды из очереди и применяет их к марионеткам через нативные хуки контроллера.
   - **Строгий инвариант:** Сетевой поток никогда не вызывает нативные методы KEX напрямую.

2. **Outbound Queue Contract (Поток симуляции KEX $\to$ Сетевой поток):**
   - Нативные перехваты KEX (хуки `Spawn`, `Damage`, `Touch`, смена карты), исполняемые в потоке симуляции, формируют структуры данных `ActorStateInfo` / `WorldEvent` и помещают их в очередь исходящих сообщений (`OutboundQueue`).
   - Нативный поток симуляции не вызывает функции сокетов ENet.
   - Сетевой рабочий поток извлекает события из `OutboundQueue`, упаковывает их в батчи по алгоритму `WorldScaleConfig` ($\le 1200$ байт) и передаёт в `enet_peer_send` / `enet_host_broadcast`.
   - **Строгий инвариант:** Функции ENet вызываются исключительно из рабочего сетевого потока.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Это внутренняя программная архитектура Sol Max Adapter; формат сообщений в сети остаётся строго неизменным.

* **Необходимость согласования с Sol:** **Да.** Требуется взаимное утверждение C++ структур очередей в интерфейсе адаптера.

## 5. Смена уровня и нативная выгрузка (Level Transition)

### 5.1 Сопоставление сетевого порядка и блокера выгрузки внешнего игрока (INC-10)

* **Сетевой протокол смены карты:**  
  В спецификации `WIRE_PROTOCOL.md` (§4.4) и приёмочном тесте 10 ([DOC-29](29_ENET_FINAL_ACCEPTANCE.md)) зафиксирован порядок:
  1. Хост инициирует смену карты: инкрементирует `mapEpoch` ($M \to M+1$), деспавнит локальные снаряды (`despawnEntity(..., MAP_TRANSITION)`).
  2. Хост рассылает надёжное сообщение `MSG_MAP_CHANGE(newMapEpoch, mapName)` по Каналу 0.
  3. Клиенты получают сообщение, сбрасывают сущности старой эпохи и отправляют подтверждение `MSG_MAP_READY(slotId, newMapEpoch)`.
  4. Хост при получении `MSG_MAP_READY` передаёт клиенту `MSG_WORLD_BASELINE` с актуальным снаряжением, ключами кампании (`teamKeyMask`) и статическими объектами нового уровня.
  5. Все устаревшие пакеты эпохи $M$ надёжно отклоняются фильтром (`staleEpochDropCount++`).

* **Нативное доказательство блокера (C19 и UNLOAD_CONTRACT):**  
  - В C19 при выходе в меню Title Screen (`StateExit` RVA `0x1401b6670` из `StateTick` `0x1401b6480`) нативный движок очистил только встроенный контекст хоста P1 (`GI + 0x118`).
  - Нативный аллокатор арены (`0x1400c58b0`) выполнил деструкцию всех марионеток уровня.
  - Однако отдельно созданный контекст внешнего игрока `Player 2` **сохранил смещение `+0xd8 = 0x133749c0`**. Этот дескриптор указывает на память в уничтоженной арене уровня!
  - При попытке тика или повторного использования контекста P2 в новом уровне неминуемо возникнет `Use-After-Free`.
  - В статическом исследовании `evidence/m0_static_respawn/UNLOAD_CONTRACT.md` Sol разработал потенциальное решение: вызов нативного `Player::Reset` (`0x1401dfa70`) для всех внешних игроков строго на входе в `StateExit` до разрушения арены.
  - Эксперимент **C20** (`C20_CONTEXT_WORLD_EXIT`) был запущен для практической проверки этого сброса, однако на момент настоящего аудита официальный отчет `RESULT.md` отсутствует, а в актуальном отчёте M0 ([DOC-27](27_M0_COMPLETION_REPORT.md)) этап M0 официально объявлен **НЕ завершённым**.

* **Реальная причина конфликта:**  
  Сетевой протокол готов к переходу уровней, но нативный движок KEX 2022 архитектурно не рассчитан на выгрузку дополнительных внешних объектов `Player` при смене карты без специального сброса.

* **Критичность:** **HIGH**. Вызывает потенциальный краш процесса хоста при переходе между уровнями кампании.

* **Статус зависимости:** **BLOCKED_BY_M0**.  
  В соответствии с правилами проекта, интеграция перехода на новую карту в сетевой слой заблокирована до тех пор, пока Sol Max официально не примет нативный контракт очистки внешних игроков в эксперименте C20.

* **Возможность исправления без изменения Wire Protocol:**  
  **ДА.** Сетевой протокол `MSG_MAP_CHANGE` / `MSG_MAP_READY` / `MSG_WORLD_BASELINE` не требует модификаций. Коррекция требуется только в нативном хуке `StateExit`.

* **Необходимость согласования с Sol:** **Да.**

## 6. Итоговые выводы и рекомендации для перехода к M1

1. **Готовность Wire Protocol:**  
   Сетевой бинарный протокол репликации мира ENet (версия 1.00, утверждённая в DOC-29) признан **полностью функциональным, математически выверенным и безопасным к интеграции**. Ни одна из обнаруженных нативных несовместимостей не требует разрушения формата пакетов, расширения заголовков или изменения 1200-байтного бюджета MTU.

2. **Обязательные точечные исправления в кодовой базе `tools/enet-prototype`:**
   - [ ] **Слоты оружия:** В `net_protocol.h` переставить местами `WEAPON_BOMBS = 3` и `WEAPON_FLAMETHROWER = 4`, добавить `WEAPON_MANACLE = 7`, установить `WEAPON_COUNT = 8`.
   - [ ] **Базовые значения:** Обновить `DEFAULT_HEALTH = 200` и `DEFAULT_PISTOL_AMMO = 60` для корректной инициализации стартовых слотов.
   - [ ] **Единицы углов:** В `client_interpolator.cpp` привести алгоритм `angleLerp` к единому базису с адаптером (нормализация радианов или работа в градусах).

3. **Обязательные требования к Sol Max Adapter (фаза M1):**
   - [ ] **Реализация двухсторонних очередей:** Внедрить `InboundCommandQueue` и `OutboundEventQueue` для гарантии 100% изоляции однопоточного KEX `simulation_tid` от фонового потока `enet_host_service`.
   - [ ] **Нативная выгрузка карт (завершение M0 C20):** Дождаться официального отчёта C20 с подтверждением очистки `Player + 0xd8` перед привязкой хуков `StateExit` к сообщению `MSG_MAP_CHANGE`.
   - [ ] **Генерация ID марионеток:** В методе спавна нового тела игрока передавать уникальный `entityId` в `MsgRespawnConfirm::newEntityId`, чтобы pending-тела прошлых поколений могли мирно сосуществовать с новыми активными игроками на стороне хоста.

4. **Заключение:**  
   По завершении Milestone M0 и реализации адаптерных очередей команда может незамедлительно переходить к сборке первого реального кооперативного сетевого прототипа P1 + P2.
