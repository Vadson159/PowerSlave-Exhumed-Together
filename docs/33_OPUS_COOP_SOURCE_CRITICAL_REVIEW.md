## 0. Главный вывод

1. Исходники описывают **lockstep-мод на PowerSlave EX public beta 1.0.0 (Kex3, x86)**. Мод написан за два дня, **2026-10-04…05** (MODLOG). Это не «кооператив 2015 года» и не «проверенные временем» решения: 2015 — год базовой игры. Часть функций сам автор помечает как непроверенные (MODLOG Stage 3: «Untested yet: … 3-4 players, travel/overworld flow, team-wipe restart in net mode, drop-out»; Stage 4.7: «No two-instance sync run yet»).
2. В lockstep-модели **нет синхронизации мира**: враги, двери, предметы и сюжет совпадают за счёт одинаковой детерминированной симуляции на всех ПК. Для нашей host-authoritative ENet-модели переносимы только **правила** (кто владеет ссылкой, кто кого атакует, что общее для команды), но не механизмы синхронизации.
3. **Старый мод ни разу не удаляет тело одного игрока посреди уровня.** Мёртвое тело остаётся в мире (`PF_DEAD`). Вышедший игрок убивается через `InflictDamage(NULL, 10000)` (`S\game\netgame.cpp:1887-1889`). Тела удаляются только полной выгрузкой карты (`S\game\world.cpp:749`). Значит, у старого мода нет готового решения для retire/sweep одного игрока, ради которого Gemini рекомендует его код.
4. Самое ценное для M0 — фактические **правила владения ссылками** в Kex3 (§2). Они объясняют наблюдения Sol и задают правильный критерий приёмки: удерживающий объект освобождает ссылку при собственном удалении, принудительный сброс не нужен. Совпадение с 2022 остаётся **INFERRED**, пока Sol не проверит его нативно.
5. В DOC-30…32 Gemini допустил несколько ошибок, опасных для M0. Главная — ложное отождествление объекта `0x160` из M0 с классом `kexFireballFactory` и вытекающие из него рекомендации ставить флаги вручную и вызывать `SetSourceOwner` на всех снарядах (§5).

## 2. Фаза 1. Фактические правила жизненного цикла объектов Kex3

### 2.1 Базовый контракт

| Правило | Источник | Статус |
|---|---|---|
| `refCount` инвазивный, без атомиков и без защиты от ухода ниже нуля | `O\game\gameObject.cpp`, `AddRef`/`RemoveRef` (`S` :59-71) | VERIFIED SOURCE |
| `SetTarget(t)`: `RemoveRef` старой цели, затем `AddRef` новой. Это единственная автоматическая ссылка базового класса | `S\game\gameObject.cpp:248-261` | VERIFIED SOURCE |
| `Remove()` **не трогает refcount**. Он только ставит `bStale` (в моде ещё отвязывает звуки) | `gameObject.cpp:77-97`; в `O` — одна строка `bStale = true` | VERIFIED SOURCE |
| `kexActor::Remove` дополнительно снимает `SOLID/SHOOTABLE/MOVEABLE/TOUCHABLE/BOUNCY` и ставит `HIDDEN/NOADVANCEFRAMES` | `actor.cpp:116-123` | VERIFIED SOURCE |
| `Removing()` = `bStale && RefCount() <= 0` | `gameObject.cpp:113-116` | VERIFIED SOURCE |
| Удалённый объект с `refCount > 0` остаётся в списке и **продолжает получать `Tick()`**. Базовый `Tick` выходит только при `Removing()`, поэтому объект живёт скрытым и инертным | `game.cpp:1535-1548`, `actor.cpp:78-82` | VERIFIED SOURCE |
| Освобождение: `UpdateGameObjects` → `RemoveGameObject` → `OnRemove()` (`link.Remove`, `SetTarget(NULL)`; у актора также `UnlinkArea/UnlinkSector/SetTaggedActor(NULL)`) → `delete`, **только если `RefCount()==0`** | `game.cpp:1687-1701`, `gameObject.cpp:103-107`, `actor.cpp:129-136` | VERIFIED SOURCE |
| Деструктор `~kexGameObject` повторно вызывает `SetTarget(NULL)` | `gameObject.cpp:50-53` | VERIFIED SOURCE |

**Следствие 1.** Удерживающий объект освобождает свои исходящие ссылки только в своём `OnRemove` или деструкторе, то есть когда **его собственный** счётчик дошёл до 0. Поэтому:

- цепочка «A держит B» штатно отпускает B через тик после удаления A;
- **цикл** «A держит B, B держит A» при обоих `bStale` не освобождается никогда до выгрузки карты.

**Следствие 2.** Удалённый объект с входящими ссылками — нормальное состояние Kex3, а не ошибка. Повторный `Remove()` безвреден, потому что он идемпотентен и не меняет refcount (`A_Destroy`, `actionDef.cpp:369-378`).

### 2.4 `RemoveAllGameObjects`: что двухпроходный алгоритм гарантирует на самом деле

Код (`game.cpp:1707-1725`, совпадает с `O\game\game.cpp:1224`):

- **проход 1:** `SetTarget(NULL)` у всех объектов;
- **проход 2:** `RemoveGameObject` у всех объектов;
- затем `gameObjects.Clear()`.

**Гарантирует (VERIFIED SOURCE):**

- все рёбра вида `target` сняты до удалений;
- объект с ненулевым refcount **не удаляется через `delete`**, поэтому use-after-free от этого цикла нет.

**Не гарантирует:**

- снятие `homingActor`, ручных ссылок `igniteFlames` и ссылок звуковых источников. `UnloadMap` вызывает `RemoveAllGameObjects` без остановки звуков (`world.cpp:745-760`); останавливает ли их раньше `kexGameLocal::StopSounds` (`game.cpp:1334-1341`), не проверено;
- удаление объекта, на который ещё держится такая ссылка. `RemoveGameObject` выполняет `OnRemove` и отвязывает объект, но при `RefCount()!=0` просто выходит (`game.cpp:1695-1698`). Это **утечка**, а в `_DEBUG` — `assert`;
- независимость от порядка списка. Пример: огонь стоит в списке раньше AI → у огня ещё refcount 1 → утечка. Огонь стоит позже → AI в `OnRemove→ClearBurn` освобождает его, и огонь удаляется нормально.

**Итог:** «двухпроходный разрыв» — это разрыв только рёбер `target` при **полной выгрузке мира**, а не механизм частичного удаления. Применить его к одному игроку, не задев мир, нельзя:

- проход 1 сбросил бы цели **всем** врагам (потеря агрессии всего уровня);
- снаряды потеряли бы стрелка: в Kex3 это ломает фильтр friendly fire (`cmodel.cpp:596-614`, `actor.cpp:501-517`), атрибуцию урона (`ai.cpp:241-249`) и, по аналогии, атрибуцию убийств для общих достижений;
- проход 2 удаляет всё.

Частичный аналог возможен только как **точечное снятие рёбер, указывающих на конкретный node, со стороны держателя и его собственным нативным setter'ом**. В коде 2015 года такого нет.

**Способ изоляции смерти в 2015:** защита стоит на **единственном месте вызова** глобального перезапуска. Тело, контроллер и мир не трогаются.

Правила старого мода (спектатор, автоматический перезапуск при гибели всей команды, сохранение оружия) **противоречат** нашим правилам и не переносятся.

### 4.4 Ответы на 10 обязательных вопросов

1. **SHA-256:** INCORRECT как криптографическое доказательство; см. 30-1.
2. **`kexFireballFactory`:** это `kexGameObject` и таймер ловушки сектора. У него переопределён `Remove` с очисткой `objectThinker`. Связи с объектом 0x160 из M0 нет.
3. **Двухпроходный `RemoveAllGameObjects`:** снимает только рёбра `target`; при оставшихся ссылках объект утекает, use-after-free нет; результат зависит от порядка списка; работает только для выгрузки всего мира.
4. **Частичное удаление игрока:** в исходниках не реализовано и через общий проход невозможно. Допустимо только точечное снятие рёбер на конкретный node нативными setter'ами держателей либо ожидание естественного ухода держателей.
5. **Native `SetSourceOwner`:** статическое окно ветки null — VERIFIED BINARY (C08). Runtime-вызов — UNKNOWN. Применимость к классам, отличным от наблюдённого actor-impact, — UNKNOWN.
6. **Ручные флаги удаления:** DANGEROUS (§5.2).
7. **Повторный декремент:** DANGEROUS. В Kex3 `RemoveRef` без защиты, а `Removing()` проверяет `<=0`. Лишний декремент позволяет удалить объект, на который ещё ссылаются, — это use-after-free. Ручная пара `RemoveRef` + `SetTarget` в `ClearBurn` корректна только потому, что `AddRef` был ручным. В 2022 sweep освобождает объект при `refs==0` (Sol). Ручной `lock dec` вместе с нативным setter'ом даст преждевременный возврат объекта в пул.
8. **Источники урона:** в 2015 инициатор урона — снаряд, стрелок — `projectile->Target()`. AI переключается на стрелка, только если это AI или Puppet (`ai.cpp:241-249`). FF-фильтр и `lastAttacker` используют того же стрелка. В 2022 по Evidence Sol:
   - melee: `source = P2 Puppet`, owner = P2;
   - basic projectile: `+0x28` = node стрелка;
   - actor-impact: `+0x148` = sourceOwner (node);
   - AI `OnDamage 0x195050` ставит `enemy+0x28` = node атакующего.

   Совпадение «снаряд держит стрелка» между версиями — INFERRED (структурная аналогия, подтверждённая статикой Sol для `0x1d50b0`).
9. **GPL:** см. 30-17 и 30-18.
10. **Даты:** см. 30-4.

## 5. Опасные рекомендации Gemini, подробно

### 5.1 Ложное отождествление «0x160 = kexFireballFactory»

Что на самом деле в M0:

- в исходнике пробы Sol (`M0_COMPLETION_20261101\NATIVE_RELEASE_SOURCE\full_player_probe.js:15,147-158`) `basic_projectile` — это **результат `SpawnProjectile` RVA `0x1d50b0`**, то есть сам снаряд, у которого `+0x28` — node стрелка;
- DOC-27 называет его «basic factory object» — объект, созданный базовой фабрикой снарядов.

В Kex3 этому объекту соответствует `kexProjectile` (наследник `kexActor`), а не `kexFireballFactory`. Аналогия Gemini неверна по смыслу класса, и все выводы, построенные на ней (M-02, Блокер 1), не имеют основания. Верным остаётся только собственное правило Sol: не передавать объект 0x160 в Actor Remove, который пишет `+0x16c`.

### 5.2 Ручная установка флагов удаления

- В 2022 (Sol, PROGRESS): `remove` RVA `0x1a02b0` → `0x1d3460` → `0x1b5530` ставит флаги `0x2004` **и помещает node в очередь `DAT_140af3380`**.
- Ручная запись флагов пропустит постановку в очередь: объект станет «удалённым» для одних проверок и никогда не попадёт в sweep для других.
- В Kex3 у подклассов `Remove` переопределён и чистит внешние сырые указатели (`kexFireballFactory`, `kexMover::Remove` — `mover.cpp:53-56`). Ручной `bStale` оставляет висячий `objectThinker` → use-after-free.
- Объект можно удалять только его собственным виртуальным `Remove` через vtable и только после проверки класса.

### 5.3 `SetSourceOwner` на всех снарядах

`0x160 > 0x148`, поэтому у basic projectile по смещению `+0x148` лежит **другое поле другого класса**. Вызов `SetSourceOwner` прочитает его как node и сделает `lock xadd [мусор+0x40], -1`. Это произвольная порча памяти.

Допустимо только то, что Sol уже предусмотрел:

- объект с наблюдённым `impact`;
- класс `actor_impact`;
- `live(rec)`;
- после возврата нативного Remove;
- ровно один вызов с проверкой `delta == -1`.
