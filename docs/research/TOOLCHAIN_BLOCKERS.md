# Инструменты: подтверждённые блокеры и обход

1. MCP REA 6.7.0 отвечает (`E000_REA_session_initial.json`), но `open_binary` с явным `provider_id=ghidra` на настоящем установленном EXE вернул `provider_unavailable` (`E001`). В окружении MCP отсутствуют GHIDRA_INSTALL_DIR/JAVA_HOME, Java fallback `java.exe` отклонён native Windows launcher: «Owned Windows process requires an absolute executable path», Win32 87. Это ошибка окружения живого MCP, а не вывод о бинарнике игры.
2. В PowerShell необходимые переменные есть. Установлены Ghidra 12.2 PUBLIC, Temurin JDK25. `rea doctor` (`E002`) принял headless, native decompiler и Java, но отклонил `application.version=12.2`: «accepted releases are 12.1.x (verified build 12.1.4)». Поэтому одного перезапуска MCP недостаточно. Не изменялись ни REA version guard, ни application.properties, ни конфигурация клиента.
3. Исправление REA в будущем: использовать совместимую Ghidra 12.1.x (проверена REA 12.1.4) с подходящим JDK; явно передать GHIDRA_INSTALL_DIR/JAVA_HOME в окружение регистрации сервера; перезапустить подключение; выполнить open_binary и настоящую декомпиляцию. Другой вариант — совместимая обновлённая REA с поддержкой 12.2. Никаких установок или конфигурационных изменений сейчас не выполнялось. Doctor сообщает также config_drift регистраций; это диагностический результат, он сам по себе не доказывает причину уже работающего MCP.
4. Независимый обход: установленная Ghidra 12.2 запускается напрямую через JDK25 и ghidra.Ghidra / AnalyzeHeadless. Это реальный анализ Ghidra, но **не работающий провайдер REA**. `invoke_ghidra.py` направляет проект, user.home, java.io.tmpdir, settings/cache/temp и логи в папку мода. ResearchExport.java экспортирует наблюдения без изменения исходного EXE. Все G_* JSON явно называют direct Ghidra fallback.
5. Первый прямой импорт с `-Xmx4G`, без ограничения analyzer workers, завершился `OutOfMemoryError: Java heap space` внутри X86Analyzer / SymbolicPropogator и Shared Return Calls. Псевдокод этим не получен; результат не считается завершённым анализом. Логи и invocation сохранены в evidence/ghidra_2022. Следующий запуск изменяет условия: `-Xmx8G`, `-Dcpu.core.limit=2`, новый локальный проект PSE_2022_cpu2. Неуспешный проект не удаляется и не принимается за доказательство.
6. PowerShell execution policy запрещает запуск локальных .ps1; настройки политики не менялись. Для разрешённых исследовательских действий используется установленный Python 3.14.6. CIM/WMI чтение OS/volume вернуло Access denied; использованы Registry/.NET: Windows NT 10.0.26300, registry display 26H2, build 26300.9711, x64, S: NTFS. Registry ProductName оставлен как наблюдаемая строка Windows 10 Pro, без попытки угадать маркетинговую версию.

MCP-операция `inspect_pe_resources` на настоящем EXE успешно выполнена (`E004`, Evidence ev_ac24f8e2f451748fad2ceeb03e1f2e9ca69a502feb27daf924cbac5936cf4f9a). Она не использует Ghidra и не доказывает исправность его провайдера.

## Результат обхода

VERIFIED: повторный импорт `PSE_2022_cpu2` завершил default auto-analysis (94 секунды по логу), сохранил локальный проект и экспортировал 10063 функции, 8547 строк с xrefs. Не отключались анализаторы. Сохраняются предупреждения отсутствующего PDB, ошибочных/неразрешённых обращений decompiler и несколько ошибок создания demangled Data; это ограничения анализа, а не доказательство порчи игры.

Первый экспорт inventory после успешного анализа записал G_INVENTORY/G_STRINGS_XREFS, но оборвался при обработке внешнего callee: собственный exporter пытался вычесть ram image base из EXTERNAL address. Исправлено явным сохранением namespace адреса и null RVA для внешних адресов; повторный автоанализ не выполнялся. Headless exit code 0 сам по себе не гарантирует успех postScript: нужно читать SCRIPT ERROR и поля Evidence.

После исправления на сохранённом проекте выполнена настоящая декомпиляция entry `0x140454a70`: `decompile_completed=true`, псевдокод вызывает `FUN_1404553f0` и `FUN_1404548fc`. Полное Evidence: `evidence/ghidra_2022/G_FUNC_140454a70.json`. Затем получены dossiers factory/load-map/start/регистрации API и instruction windows getter callbacks. Это прямой Ghidra 12.2, не REA Ghidra.

Дополнительная реальная попытка CLI `rea decompile` с фактическим entry file offset `0x453e70` сохранена в E012: CLI также не дал декомпиляцию из-за неподдерживаемой версии 12.2. Повторять тот же вызов до изменения окружения/совместимости бессмысленно.
