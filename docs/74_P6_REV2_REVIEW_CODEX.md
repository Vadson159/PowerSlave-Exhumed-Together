## 1. R2-F1 — после anchor не определён выход к сравнению с history (P1)

**Место:** DOC-62 §3.4 T2/T5, строки 103 и 111–115 проверенной редакции; точный текст/номера — [EXCERPTS](evidence/m1/P6_REVIEW_REV2_CODEX/EXCERPTS.json), неизменный [снимок DOC-62](evidence/m1/P6_REVIEW_REV2_CODEX/REVIEWED_DOC62.md). Метка вывода — **INFERRED**, следствие правил спецификации; не наблюдение KEX.

T5 очищает history, устанавливает свежий anchor, начинает новую predictionGeneration и возобновляет ввод. T2 пишет history после локальных шагов и требует две записи, охватывающие время snapshot. При отсутствии пары T2 без исключения направляет в T5. Контракт не задаёт обязательную начальную запись новой history, нижнюю границу принимаемого времени после reset или фазу ожидания её заполнения.

В допустимом расписании первый обычный snapshot приходит уже **после принятия ACK хостом**, но относится ко времени раньше первой post-step записи новой history:

| Событие | Синтетическое монотонное время |
|---|---:|
| Хост снимает anchor, position=100, velocity=0 | 100 |
| Клиент применяет свежий anchor; history пуста | 103 |
| Хост принимает ACK | 104 |
| Хост снимает обычный snapshot того же token/discontinuity; position=100 | 104,2 |
| Первые две post-step записи новой history | 106 и 107 |
| Клиент обрабатывает snapshot: tau=104,2 вне history | 107 |

Здесь реальная позиционная ошибка нулевая, поколения совпадают, оценка offset=0 с допустимой uncertainty=0,5. Из T2 следует WAIT_ANCHOR, а из T5 — новый token и повторное уничтожение history. Аналогичное расписание для следующих двух tokens снова даёт WAIT_ANCHOR. Ожидание ACK на хосте само по себе этот случай не закрывает.

[RESET_HISTORY_COUNTEREXAMPLE](evidence/m1/P6_REVIEW_REV2_CODEX/RESET_HISTORY_COUNTEREXAMPLE.json) хранит три шага. [Скрипт](evidence/m1/P6_REVIEW_REV2_CODEX/review_rev2.py) последовательно вызывает **существующие чистые fixtures автора** `reset_projection()` и `history_status()`, не меняя их: первый возвращает ACTIVE/history=[], второй — WAIT_ANCHOR. Это показывает отсутствие обязательного правила обеспечения прогресса; не утверждается, что любая возможная реализация неизбежно зациклится. Реализация может избежать проблемы дополнительным правилом, но сейчас его пришлось бы придумать в П7 вместо исполнения однозначного ADR.

**Требуемая правка:** определить переход от установки anchor к первой допустимой паре history: обязательный seed/его время, временную границу новой predictionGeneration и поведение с samples до этой границы. Разделить первоначально ещё не накопленную history и историю, потерянную после нормального сравнения. Ранний sample в период заполнения не должен автоматически создавать следующий reset; ожидание ограничить бюджетом и явно задать timeout/новый разрыв. Семантику времени seed нельзя подменить старым host stateTime так, будто клиент физически находился в новой позиции до установки anchor.

Добавить составной offline-сценарий «reset → anchor → ACK → ранний обычный snapshot → накопление history → первое успешное сравнение», а не только отдельные проверки reset и missing history. Нужны также варианты задержки, reordered samples и действительно истёкшей history. Реальные нативные hook/движение/пороги остаются gate П7; новый игровой run для исправления ADR не требуется.

**Вердикт ADR-1:** REQUEST CHANGES / REJECT текущего перехода T2/T5. A остаётся кандидатом; переход к B или lockstep этим замечанием не требуется.
