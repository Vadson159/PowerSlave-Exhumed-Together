# PowerSlave EX (2015) → PowerSlave Exhumed (2022) — Матрица переиспользования решений

**Дата актуализации:** 2026-11-01  
**Назначение:** Приоритетная матрица алгоритмического и архитектурного переноса решений старого кооператива (2015, x86 KEX3, GPL) в новый мод PowerSlave Exhumed Together (2022, x64 KEX4, C++ hook).

## 1. Общие принципы портирования и барьеры совместимости

> [!CAUTION]
> **Прямое бинарное копирование структур, указателей и оффсетов между x86 KEX3 (2015) и x64 KEX4 (2022) категорически недопустимо!**

### Ключевые различия подсистем:
1. **Разрядность и ABI:**
   - 2015: 32-битный x86 (`__thiscall` для методов классов, аргументы в стеке, `ecx = this`).
   - 2022: 64-битный x64 (Microsoft x64 ABI, `rcx = this`, `rdx, r8, r9` в регистрах, теневое пространство стека 32 байта, выравнивание 16 байт).
2. **Управление памятью акторов:**
   - 2015: Динамическая аллокация кучи (`new` / `delete`) с простым инвазивным счетчиком ссылок `refCount` внутри объекта.
   - 2022: Фиксированные пулы объектов (Object Pools) с внешними дескрипторами `ObjectNode` (`node->payload`, `node->refcount` на `+0x40`), отложенным сбором (deferred retirement sweep `FUN_1401b6360`) и строгим возвратом в пул только при `node->refcount == 0`.
3. **Сетевая парадигма:**
   - 2015: Детерминированный локстеп (Lockstep) с обменом командами ввода `netCmd_t` и синхронизацией PRNG seed на старте уровня.
   - 2022: Host-Authoritative Entity Replication на базе ENet (DOC-29), где хост симулирует мир целиком и реплицирует снапшоты сущностей с частотой 24–30 Гц. Перенос локстепа исключен.
4. **Лицензионная изоляция:**
   - 2015 исходники распространяются под лицензией GPLv2. Прямой перенос исходных строк кода в закрытую кодовую базу мода для 2022 нарушит лицензионную чистоту. Переносятся исключительно **алгоритмы, эвристические формулы и последовательности вызовов (clean-room reimplementation)**.

## 3. Детальный разбор критических для Sol Max решений (P0 Focus)

### Решение M-01: Двухпроходный разрыв циклических ссылок при Teardown

- **Проблема в 2022:** В C08 и C10 при уничтожении врага его `ObjectNode` удерживался со значением `refs = 1` из-за того, что активный снаряд или эффект удара хранил ссылку на узел врага через поле `sourceOwner` (`+0x148`).
- **Как это решалось в 2015 (`game.cpp:1229-1233`):**
  Движок KEX никогда не пытается удалять объекты, пока на них есть ссылки. На этапе зачистки карты или выхода игрока выполняется явный предварительный проход:
  ```cpp
  for(go = gameObjects.Next(); go != NULL; go = go->Link().Next())
  {
      go->SetTarget(NULL);
  }
  ```
- **План действий для Sol Max в 2022:**
  1. Перед возвратом P2 или тестового врага в пул убедиться, что все связанные с ними акторы (снаряды, эффекты ударов) выполнили обнуление своих полей `target` (RVA `0x1d35d0`) и `sourceOwner` (RVA `0x1a17c0`).
  2. Никогда не выполнять жесткий декремент счетчика `lock dec [node + 0x40]` вручную — использовать только нативный сеттер с аргументом `RDX = NULL`, который выполняет штатный атомарный декремент старого узла.

### Решение M-02: Разделение жизненного цикла `kexGameObject` и `kexActor` (0x160 vs 0x16c)

- **Проблема в 2022:** Попытка вызвать `Actor::Remove` (RVA `0x1a02b0`) для объекта фабрики снарядов размером 0x160 приводит к порче памяти.
- **Как это устроено в 2015:**
  - `kexFireballFactory` — это `kexGameObject` (базовый объект).
  - `kexActor` — наследник `kexGameObject`, добавляющий 12 байт физических флагов и связей.
  - В x64 смещение полей актора увеличивается. Функция `kexActor::Remove` пишет `[rcx + 0x16c] |= 0x2004`. Если объект имеет размер 0x160, происходит запись за пределы выделенного блока.
- **План действий для Sol Max в 2022:**
  - Проверять vtable объекта перед вызовом Remove.
  - Для объектов размером 0x160 вызывать базовый деструктор/сеттер флагов объекта, никогда не вызывая `Actor::Remove`.

### Решение M-03: Упреждающий сброс целеуказания при смерти актора

- **Проблема в 2022:** Если враг убит, пока к нему летит снаряд, снаряд удерживает ссылку на труп врага до момента своего падения или взрыва.
- **Как это решалось в 2015 (`projectile.cpp:111`):**
  В каждом тике полета снаряда в `HomingThink` проверяется состояние цели:
  ```cpp
  if(homingActor->Removing() || homingActor->Health() <= 0)
  {
      SetHomingTarget(NULL);
  }
  ```
- **План действий для Sol Max в 2022:**
  - В хуке обработки смерти актора (`OnDeath` / `InflictDamage` со смертельным исходом) сканировать пул активных снарядов и обнулять их целевые ссылки на погибшего актора. Это позволит узлу погибшего врага сразу получить `refs = 0` и вернуться в пул без ожидания падения всех снарядов.
