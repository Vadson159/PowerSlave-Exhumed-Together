# M1.1 Direct Quit — FINAL PASS

**PASS для существующей exact-build DLL и принятого Direct Quit. M1.1 готова к началу сетевой интеграции M1.2 как native foundation.** ENet/Thread Bridge не подключались, M1.2 не начинался. Дополнительных игровых запусков — **0**; DLL не редактировалась и не пересобиралась.

Закрыт именно lifetime-пробел [DOC-42](42_M1_DIRECT_QUIT_SAFETY.md): использовано доказательство владения ресурсами вместе с уже полученным runtime, разрешённое текущим заданием. **OS ExitProcess checkpoint M11B не наблюдался и не объявляется наблюдавшимся.** Его отсутствие теперь является ограничением telemetry, а не основанием считать lifetime неопределённым.

## Почему достаточно существующих доказательств

EXE SHA-256 `b8f131037187ca8d0a282527fb6f55a2012241d5b9dac8bf2038baf35b71a76d`; DLL SHA-256 **`0cb84521c47dddd20bdebf3a2f42dda79f2f50ef1cfc3c280c14878812648629`**. Проверенные исходники совпали с [manifest принятой сборки](evidence/m1/M11_IMPLEMENTATION_20261101/BUILD_20261101_202721_800243.json). Полный разбор, excerpts с line numbers/хешами и результаты — [LIFETIME_PROOF](evidence/m1/M11_DIRECT_QUIT_FINAL_20261101/LIFETIME_PROOF.json).

1. **DLL-код и Player storage — process lifetime.** `M11Prepare` до установки hooks успешно выполняет `GetModuleHandleExW(FROM_ADDRESS|PIN, &M11Prepare, …)`; native `dll_prepared` записывается только после успеха. Windows PIN удерживает определяющий образ до завершения процесса, включая вызовы FreeLibrary. [Контракт Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandleexw). Player/guards/таблица original pointers находятся в статическом `Context g` этого образа, а не в JS-heap или отдельном освобождаемом allocation. [Compile-only static_assert](evidence/m1/M11_DIRECT_QUIT_FINAL_20261101/CONTEXT_CHECK.json) подтвердил trivial destruction Context/GuardedPlayer; собственный DllMain на detach ничего не освобождает. Это распространяется и на код VEH callback.
2. **Original trampolines не освобождаются при restore.** В используемом статически встроенном MinHook `MH_DisableHook → EnableHook(FALSE) → EnableHookLL` восстанавливает target bytes и управляет thread scratch; кодовые VirtualAlloc blocks не освобождает. Их release возможен через RemoveHook/Uninitialize либо ошибку создания. Adapter не вызывает эти release routines; все CreateHook находятся только в bootstrap, успешность которого подтверждена до P2. Автоматического MinHook detach cleanup в CMake-составе DLL нет. HeapFree списка thread IDs при disable не является освобождением trampolines.
3. **Runtime проверяет предпосылки и реальный shutdown.** [M11B journal44–55](evidence/m1/M11B_DIRECT_QUIT_01/LIFECYCLE.json): живой P2 health200 → exact restore четырёх control entries → один Reset/handle0/P1 unchanged → services cleanup → выполнение native final callback; guards=true, foreign_calls0, ticks_after_shutdown0, StateExit/owned destructor0. [До Quit](evidence/m1/M11B_DIRECT_QUIT_01/load_direct_quit_observer.json) реально mapped DLL storage/10 callbacks и private MinHook allocation. [C25](evidence/m0/C25_NATIVE_DIRECT_QUIT_BOUNDED/RESULT.md) задаёт принятый процессный exit contract, [DOC-41](41_M1_NATIVE_BOOTSTRAP.md) — native ABI/lifecycle foundation.

**Следствие, а не новый OS-снимок:** образ и storage удерживает OS PIN; у частных trampoline allocations нет достижимого release в этом shutdown. Поэтому callback/return addresses остаются обеспечены памятью до OS process reclaim независимо от регистрации конкретного terminal export. Это опирается на положительные runtime witnesses и проверенные ownership paths, не на один exit0 или отсутствие записанных FreeLibrary/VirtualFree событий. Повторить старый Frida observer либо ставить debugger breakpoint для этих инвариантов не требуется.

## Почему мог отсутствовать OS record

**Установленный недостаток наблюдаемости:** в [исполненном probe](evidence/m1/M11B_DIRECT_QUIT_01/direct_quit_probe.js) `m11b_os_exit` отправляется только после вычисления полного `snapshot()` с NativeFunction(VirtualQuery) и чтениями памяти. Отдельного durable entry-marker до snapshot нет. Следовательно, отсутствие сообщения не различает «onEnter не вызван» и «вызван, но snapshot/send не завершён».

В [Frida17.23.2 ExitMonitor](https://github.com/frida/frida-core/blob/17.23.2/lib/payload/exit-monitor.vala) Windows ExitProcess также является границей собственного exit monitor; [agent preparation](https://github.com/frida/frida-core/blob/17.23.2/lib/agent/agent.vala) проходит через подготовку sessions/scripts. Взаимодействие этой подготовки, порядка listeners/доставки JS и тяжёлого snapshot — **возможное объяснение**, не установленная причина M11B. Нельзя утверждать автоматический detach всех observers либо фактический обход ExitProcess. Точный порядок и версия agent в M11B не записаны; фактическая причина остаётся **UNKNOWN**. [Сохранённые primary sources](evidence/m1/M11_DIRECT_QUIT_FINAL_20261101/PRIMARY_SOURCES.json). Это не влияет на доказательство lifetime native DLL, не зависящее от жизни JS observer.

## Граница решения и остановка
